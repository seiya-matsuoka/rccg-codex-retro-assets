# 実装に対応したプロジェクト文書を整える

読者が現行の使い方・仕様・構成を理解できる文書を作る。
実行結果を中心とする報告書への置き換えや、既存文書の一律な短縮は行わない。

## 文書の役割を確かめる

依頼対象、読者、文書の役割、変更してよいファイル、完了条件を確認する。
既存の README、仕様書、設計書、文体・構成・粒度を示す見本を必要な範囲で読む。
次の区別を確認し、対象の方針を優先する。

- 計画として固定する文書と、現在の仕様に合わせて更新する文書。
- 単独で現行仕様を説明する文書と、変更点だけを示す文書。
- 利用者向けの案内、開発者向けの設計説明、検証・開発の記録。
- 本文として維持する章・表・式・詳しい説明と、参照で足りる情報。

目的や粒度が不明で、大量の書き直しにつながる場合は、短い構成案や一節の記述例で確認する。
既に合意された構成や軽微な文章修正に、毎回追加の承認工程を設けない。
自分で作る次工程の依頼文にも、元の読者・役割・保存方針・維持する内容を引き継ぐ。

## 現行状態を根拠に書く

関連する実装、型、設定、manifest、テストを確認する。
計画との差があれば、合意済みの変更と、判断が必要な未解決事項を区別する。
過去の記録やコメントだけで、現在の動作を断定しない。

- セットアップ・実行コマンドは、実在する設定と実行場所を確認する。
- 保存、通信、失敗・取消、対応環境など、利用や設計判断に関係する制約を説明する。
- テストがあること、過去に通ったこと、今回実行したことを分ける。
- coverage の対象外、手動確認、CI、公開環境、実機確認の範囲を混同しない。
- 実行していない確認は、必要なら未実施と示す。
  文書のためだけに、未許可のサービス起動や外部操作を追加しない。

確認できない情報は推測で埋めず、不足が記載内容を左右する場合だけ確認する。

## 許可された文書を作成・更新する

既存の章や表を維持する依頼では、その本文を現行仕様に合わせて更新する。
章を残して内容を参照リンクだけに置き換えたり、式・条件・詳細を独断で省略したりしない。
全面的な再構成や要約が目的なら、その依頼に沿う。

実行回数、commit、CI の run、検証ログ、開発の時系列は、文書の目的に必要な場合だけ含める。
現行仕様を説明する文書へ、開発記録を主目的として混在させない。
同じ仕様の記載先が複数ある場合は、正となる場所と参照関係を整理し、無関係な文書へ更新を広げない。
README の作成時期、計画の保存方法、ファイル名は対象のルールに従う。

コード・テストの修正、AGENTS.md・設定の変更、依頼対象外の画像・新規文書の追加は、文書整備の依頼から自動で許可されたと扱わない。
必要なら具体的な対象と理由を示す。

## 完了を確認する

- 本文の振る舞い・制約・コマンドが、確認した実装と一致しているか。
- 既存の章・表・式・必要な説明を、合意なく失っていないか。
- 参照リンク、相対パス、見出し、コードフェンスに破損がないか。
- 新規・未追跡ファイルも確認対象に含めたか。
- 保証の記述が、実装・テスト・実際の確認範囲を超えていないか。

利用可能な既存の文書チェックがあれば、許可範囲内で実施する。
確認のための新しい依存取得や、範囲外の整形は行わない。
変更ファイル、参照した根拠、実施した確認、未確認・未解決事項を報告する。
公開や Git 操作は、それぞれに明示的な依頼がある範囲だけで扱う。
