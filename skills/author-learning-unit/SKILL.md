# 指定した学習 Unit の教材を作成する

教材作成者として、学習目標に対応したコードと説明を整える。
教材の生成・検証と、学習者本人の理解・習得を区別する。

## Unit と工程を確定する

カリキュラム、学習運用、サンプル仕様、適用ルール、近い Unit の教材を必要な範囲で読む。
次を既存情報と依頼から確認する。

- 対象 Unit、今回の工程、変更できるファイル、停止条件。
- 到達目標、前提知識、今回初めて導入する概念、扱わない内容。
- 共通サンプルを育てる構成か、Unit ごとに独立させる構成か。
- 完成コードを読む方法か、演習・穴埋めを含む方法か。
- README とコードの工程分離、レビューのタイミング、標準とする解説・コメントの粒度。

コード確認後に README を作る運用なら、指定工程の範囲を守る。
README のみの依頼をコード修正の許可として扱わない。
その分離がない運用へ、別のリポジトリの工程を一律に強制しない。
古い進捗、引き継ぎ、受け渡し方法が現在の指示と食い違う場合は、役割と合意を確認する。

## 学習目標と教材を対応させる

各目標について、コードや操作の例、観察する結果、説明する理由が揃うか確認する。
新しい形式で粒度が未定なら、必要に応じて短い例で認識を揃える。
一律の行数制限やすべての Unit への同じテスト・演習の追加は行わない。

既存の技術構成を使い、教材作成の都合で新しいフレームワークや依存を導入しない。
説明用アプリの機能や抽象化を増やしすぎず、学習対象の概念を読み取れる構成にする。
完成コードを読む方針なら、TODO や未完成のテストを勝手に混ぜない。

共通サンプルや過去 Unit の変更が依頼範囲に含まれるか確認する。
含まれない変更が必要なら、理由、影響、変更案を示して許可を求める。
後続テストを通すためだけに正本を変更したり、比較に必要な段階別の例を統合したりしない。
必要な補助例は、許可された配置で正本と区別する。

## コードと観察を確認する

既存のコマンドと設定を使い、許可範囲で実行・型検査・テスト・静的解析を行う。
すべての技術に同じ runner や検証構成を要求しない。
依存取得、外部通信、サービス・コンテナ起動、永続データ操作が必要なら、対象と条件への許可を確認する。
構成図や技術選定だけを操作の許可としない。

学習対象に応じ、次のような観察を選ぶ。

- 出力順、終了コード、標準エラー、ファイル内容、入力前後の状態。
- 型検査で検出する条件と、実行時に発生する条件の違い。
- HTTP・DB の境界、テストが本物と置き換えをどこで使うか。
- コンテナやデータの状態、複数セッションの役割、操作順に依存する結果。

意図的な失敗例は、予告した条件と失敗を確認し、通常の成功例と区別する。
失敗例を自動で正常化せず、失敗する理由と改善後の違いを説明する。
期待と異なる失敗や、教材と実行結果の不一致は調査する。
環境で変わる時間・性能・出力を固定の保証として書かない。
必要な複数セッションを単一実行で代用した場合など、確認範囲が足りなければ明示する。

## 許可された解説を作成する

実際に作成・確認したコードを根拠に、概念、処理順、責務、入出力、失敗時の扱いを説明する。
既存の必須構成と粒度を維持し、初見の構文・API・テスト技法の役割を省略しない。
コードコメントには、その箇所の前提、採用理由、仕様との対応、Fixture・置き換え・Assertion の意味を対象に応じて残す。
README とコメントを補完させ、必要な説明を重複回避だけの理由で削らない。
コメントや説明に、実装していない保証や未実施の検証を含めない。

README を別工程で作る場合は、今回確認したコード、未検証の条件、次に参照する場所を報告する。
その報告を README 作成や次 Unit の開始許可としない。

## 終了時に確認する

到達目標と例・説明の対応、前提知識、難易度、意図した結果、コードと解説の整合性を確認する。
教材の作成済み範囲、実際に検証した範囲、未実施の条件を報告する。
学習者の学習済み状態は推定せず、進捗記録の更新も依頼範囲に従う。
指定 Unit・指定工程の終了条件で停止し、次 Unit やカリキュラム全体の生成へ進まない。
