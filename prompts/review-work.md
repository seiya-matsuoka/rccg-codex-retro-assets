# 作業結果をレビューするためのプロンプト

実装、設定、文書、教材を、変更目的と重要な境界から確認する場合に使用する。
独立した確認が必要なら、別チャットへ対象と参照先を渡して使用できる。
このファイルの利用自体は、別チャットや Subagents の作成・委任を許可しない。
`{{...}}` を具体化し、未指定の軽微な条件は既存情報から補う。

## 依頼本文

```markdown
以下を読み取り専用でレビューしてください。
コードや文書の修正、設定変更、Git・GitHub の状態変更、Subagents の使用は自動で開始しないでください。

- 対象リポジトリ：{{絶対パス}}
- レビュー対象：{{未コミット差分、比較対象、機能、指定ファイルなど}}
- 目的・受け入れ条件・参照先：{{仕様、計画、Issue、教材の狙いなど}}
- 重点：{{コード／設定／文書／教材。複数可}}
- 実行確認の許可範囲：{{既存のオフライン検証など。未指定は静的確認のみ}}

### 対象と基準の確認

作業先、branch、git status、適用ルールを確認し、今回の対象と既存変更を区別してください。
未追跡ファイルや追加ファイルも対象か確認し、git diff だけで全件確認したと扱わないでください。
正となる仕様、実装、文書の役割を確認し、開発途中の計画や古い進捗から現在の保証を推定しないでください。
指定範囲から呼び出される処理や状態の関係は、指摘の根拠に必要な範囲で追ってください。

### 重点に応じた確認

- コード：入力境界、非同期の完了順、古い結果の反映、状態遷移、失敗・取消後の状態を確認してください。
  保存・API・DB をまたぐ操作は、成功・途中失敗・再試行時の整合性と、利用者が観測する結果を確認してください。
- 設定：実際のコマンド、環境変数の前提、実行場所、出力先、外部通信、CI とローカルの違いを確認してください。
  テスト用データや処理が、利用者のデータ・既存プロセス・永続環境へ影響しないかを対象に応じて確認してください。
- 文書：読者と役割、現行実装との一致、リンク、コマンド、構成・表・式・重要な説明の欠落を確認してください。
  計画、現行仕様、実行ログを区別し、未実施の検証を保証として記載していないか確認してください。
- 教材：到達目標、前提知識、難易度、コメント・解説とコードの対応、予告した実行結果を確認してください。
  意図的な失敗例、段階別の独立性、学習上必要な重複は、目的を確認して評価してください。
  通常のリファクタリング基準だけで、例や詳しい説明の削減を指摘しないでください。

既存テストがどの境界を検証し、どこを検証していないか確認してください。
coverage の数値やコマンド成功だけで、UI、非同期、API、DB、説明の正しさまで保証されるとは扱わないでください。
逆に、テストがないことだけで不具合と断定せず、必要な保証と影響を説明してください。

### 実行確認

再現が必要で、今回の許可範囲に含まれる確認だけ実施してください。
読み取り専用レビューでは、ソース、設定、snapshot、固定された資料を更新しないでください。
許可された検証の cache・生成物も出力先を確認し、外部通信・追加依存・サービス起動・永続データ更新は、許可がなければ行わないでください。
実行できない条件は静的推論として示し、再現済みとは書かないでください。

### 報告

問題がある場合は、影響の大きい順に次を示してください。

- 対象ファイルと位置。
- 発生条件、期待と実際の差、利用者または学習者への影響。
- 根拠となる処理・仕様・再現結果。
- 確認済みの事実と、未確認の仮説。
- 必要な修正の方向と、確認すべき条件。

好みの変更、将来の改善候補、仕様確認が必要な事項は、不具合の指摘と区別してください。
問題が見つからなかった場合も、確認範囲、実施した検証、未確認の境界を示してください。
指摘数を増やすことを目的にせず、修正は別の依頼を待ってください。
```
